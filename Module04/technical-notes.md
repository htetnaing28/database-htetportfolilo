# Integrity at the edge

schema.sql contains the course STRICT schema, PK/NOT NULL/UNIQUE/FK/CHECK constraints, virtual generated value, replay key, alarm/audit triggers and machine_health view. Invalid type, range, NULL, interval, orphan and duplicate-sensor statements are executed individually; exact errors are in results.json. CHECK alone accepts NULL: NOT NULL is a separate requirement. Plausible but wrongly attributed readings still pass without external truth.

readings.csv is replayed twice using parameterized executemany UPSERT; row count stays two. ingest.py accepts only an existing generated Module04/artifacts database, enables FKs, commits atomically and updates both value and interval. Run it with the edge.db path in evidence/latest.json. Replayed unchanged values still produce an audit entry under the supplied AFTER UPDATE trigger. Alarms represent insert events only: correction-on-update is not a complete current-alarm state model. Audit UPDATE/DELETE guards protect ordinary DML, not a file owner who can drop triggers.

The generated energy_j=value×interval_s is retained to match the exercise, but temperature×seconds/vibration×seconds is not energy in joules. A real energy model needs a power metric with compatible units. Trigger overhead compares fresh in-memory databases with 10,000 over-threshold inserts, five runs, same audit schema; alarm allocation is part of the enabled workload. This is not durable disk throughput.

The mode=ro demonstration actually refuses DELETE and reads the view. A view does not restrict direct access to base tables. SQLite has no GRANT roles: use OS ACLs for the whole file and readonly handles for cooperative readers. On Windows, inspect `icacls <generated-edge.db>` and grant a dedicated reporting account read-only access through File Properties/Security; [STUDENT INPUT REQUIRED: Apply and test with the actual reporting identity]. POSIX chmod is not available in this PowerShell workflow, and changing this owner's permissions would not prove a second user's isolation. PostgreSQL roles can grant per-table access and handle independent network identities; a shared writable SQLite file is unsuitable as a multi-tenant trust boundary.
