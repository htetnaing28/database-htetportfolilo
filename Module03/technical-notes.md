# Queries, plans and security

setup.sql reproduces the supplied 2,000 customers, 500 products, 60,000 orders and 240,000 lines. Duplicate line products in the generator are intentional source data, not deduplicated revenue. Prompt: “Return each city's distinct ordering customers and revenue from orders placed in 2025, ordered by revenue.” The AI-assisted implementation uses the course reference query; it is not attributed to a fictional separate model session. Independent Python grouping/set aggregation verifies every result. Customers without qualifying orders are excluded by inner joins; a zero-revenue-city requirement would need a different query.

Engineering prediction: scan the fact lines, search dimension PKs, temporary structures for grouping/distinct/order. [Actual plans](evidence/results.json) are the authority. Each proposed index is tested independently against the same baseline, with warmup and five samples. The selective lookup is amortized over 100 executions per sample. date(ordered_on) is the negative example: an ordinary index does not directly index the expression. An index that is unused by this dashboard can still help a different product-selective workload; no index is universally useless.

Algebra: τ_revenue↓ γ_city;count-distinct(customer_id),sum(qty×price) (σ_2025 (Customer ⋈ Orders ⋈ OrderLine ⋈ Product)). Filtering occurs before aggregation; the customer count uses sets rather than line counts. SQL has bag semantics, so distinct must be explicit. Logical order is FROM/WHERE/GROUP/HAVING/SELECT/ORDER; SQLite allows some aliases in WHERE as an extension, so the workbook's universal alias-crash claim is not portable.

The isolated injection drill returns 2,000 customers for `' OR '1'='1` using intentionally vulnerable concatenation, zero using binding, and captures the apostrophe syntax error. Binding keeps values out of the SQL grammar; ad-hoc quote filtering is context-dependent and breaks legitimate names. Identifiers must come from an allowlist, not a value placeholder.
